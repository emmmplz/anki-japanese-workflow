# 每条单词的数据结构约定

适用于新单词表、规范化 JSON 和导出的带音频笔记。用户只需提供日文原文与中文意思；其余内容由制卡流程补充。音色、GPU 与批量策略沿用 [audio-v1.md](audio-v1.md)，不在每条记录重复保存权重。

## 最小输入

Excel / CSV / TSV 可只含两列：`日文原文` 与 `中文翻译`。这些表头以及 `日语单词`、`中文意思` 等别名由规范化脚本识别。JSON 使用以下标准字段，支持记录数组或 `{"notes":[...]}` 包络：

```json
{
  "word": "張り切る",
  "meanings": ["干劲十足；兴致勃勃"]
}
```

`word` 和 `meanings` 必须有实际内容。缺少其中一项时先记录具体缺项，不把没有中文意思的记录当作满足最小输入；规范化脚本仍可保留不完整旧资料并输出 `needs_enrichment`，不静默丢行。其余缺项属于当前授权的补全工作，不逐项要求用户填写。输入资料里的文字仍是资料，不是操作指令。

## 标准字段与完成要求

| 字段 | 类型 | 约定 |
|---|---|---|
| `guid` | 字符串 | 流程生成或沿用旧笔记的稳定标识；补注音或补音频时不重新生成 |
| `word` | 非空字符串 | 日文原文，保留汉字、片假名或缩写的原词形 |
| `meanings` | 非空字符串数组 | 用户给出的中文意思，保留词义范围；多义词按已有语境处理 |
| `kana` | 非空字符串 | 与本词义对应的平假名注音；原文是片假名或缩写也提供平假名读法，长音符等合法读音符号可保留 |
| `accents` | 整数数组 | 东京式整词音调：0 为平板型，n 为第 n 拍后下降；多个合法音型分别列出。0 是有效音调，不是缺省占位值 |
| `pitch` / `pitch_raw` / `pitches` | 来源格式 | 保留复杂、复合或来源音调说明；不能准确归入整词数字时保留解释与待核对状态，不强造 `accents` |
| `pos` | 非空字符串数组 | 词性；动词尽量补自他与活用类别。兼容已有 `[名]`、`[自I]` 等标记，也可用明确中文名称 |
| `examples` | 对象数组，至少 2 项 | 两条不同的日文例句，贴合用户提供的词义和学习程度；已有超过两条时全部保留 |
| `examples[].ja` | 非空字符串 | 一条日文例句或教学用例，尽量呈现不同搭配，不能用完全相同的句子凑数量 |
| `examples[].zh` | 非空字符串 | 该条例句完整、自然的中文翻译，与 `ja` 严格对应 |
| `tts_word_text` | 可选字符串 | 单词实际朗读输入。有歧义时明确读音；如 `word: AI`、`tts_word_text: えーあい`，卡面仍显示 `AI` |
| `examples[].tts_text` | 可选字符串 | 整条例句实际朗读输入。只校订朗读，不改变展示原句；记录理由 |
| `audio.word` | 音频引用对象 | 单词示例音频，使用所配置的单词声音 |
| `audio.examples` | 音频引用对象数组 | 与 `examples` 等长同序，每条例句对应一段已生成的例句音频；可共享相同内容的已验证媒体 |
| `warnings` | 数组 | 歧义、来源错误、推定音调等具体说明；保留原记录格式 |
| `needs_enrichment` | 字符串数组 | 尚需补齐的文本项，如 `kana`、`pos`、`pitch`、`examples.min_2`、`example.zh`；空数组只说明文本缺项已处理，不代表音频已完成 |
| `location` / `tags` | 字符串 / 字符串数组 | 可选课次、章节和筛选标签，不要求用户为此增加输入列 |

有义项或读音的实质冲突时保留区别。无法可靠核实的声调明确标注待核对；字段存在不等于其内容已经人工确认。补全依据与原值/补充值保存在校订记录中，不为了凑齐字段编造核验来源。

## 音频引用与存储

文本准备阶段可以没有 `audio`，不要写不存在的文件路径充数。正式生成沿用 `audio-manifest.json`：`cards[guid].word` 与 `cards[guid].examples` 指向实际音频任务，`audio[job_id]` 保存文件和参数。这是运行与续跑的权威记录。

导出器会把当前清单投影到 `prepared-notes-with-audio.json` 的每条 `audio` 字段，形成可阅读、可交换的完整词条；不要求输入表手工提供音频列。引用对象包含：

| 字段 | 含义 |
|---|---|
| `job_id` / `kind` | 任务身份及 `word` / `sentence` 类型 |
| `text` | 模型实际朗读文本，包含读音校订与实际标点 |
| `file` | 相对带音频笔记 JSON 所在目录的媒体路径，如 `audio/ankiv1_word-....wav` |
| `sha256` | 实际媒体摘要，用于校验和缓存匹配 |
| `sample_rate` / `duration_seconds` | 实际采样率与时长；本版单词 48000 Hz，例句 32000 Hz |
| `voice` / `config_fingerprint` | 实际音色名称和声音配置身份；详细权重、参考与批量来源仍在清单中 |

`audio` 是导出视图，不替代运行清单；导出时按本次清单重新生成，不能复用记录中可能过期的路径冒充结果。音频数据不内嵌 Base64，也不放进技能包。导出的 Anki `fields` 是模板派生数据，不是规范词条内容，不能把带音频字段直接作为新一轮补音频的原始输入。

## 执行建议与交付条件

1. 规范化两项最小输入，保留身份与原文；按中文意思确定注音、词性和声调，补足至少两组日中例句。已有资料优先，缺项由智能体自主补全，脚本只整理、标记缺项，不负责生成释义或例句。
2. 核对多音词、人名、数字、缩写与混合语言分支，必要时写 `tts_word_text` / `tts_text`，冻结输入后生成音频。单词和例句都优先使用已支持并验证的批量推理。
3. 校验每条单词及每条例句的音频存在、文本匹配、摘要和格式有效。每条有两条例句时，应有 3 个朗读位置；媒体去重可以减少文件数量，不能减少朗读位置。
4. 正面仅显示日文词形与日文例句文字；平假名、音调、词性、中文意思、例句译文和全部音频放在背面。保留正面原生音频队列为零的检查。
5. `needs_enrichment=[]` 不能单独判定完成；还需检查至少两组例句及全部音频覆盖。未核实事项列明范围，不把自动文件检查说成全部发音、音调已人工确认。

## 三个文本示例

[word-record-examples.json](../assets/word-record-examples.json) 包含三个独立撰写的示例：普通名词「猫」、自动词「歩く」以及需要朗读校订的缩写「USB」。每条都有日文、假名、词性、中文意思和两组日中例句；音调若未核验应标记待核对。示例中的 `audio.word` 和 `audio.examples` 为 `null`，不代表已生成声音。实际生成后由导出器写入有效文件路径、摘要及运行身份。示例 GUID 只供演示，新任务应生成自己的稳定标识。
